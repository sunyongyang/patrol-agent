# 飞书开放平台配置清单（巡逻 Agent Demo）

> 配套文档：[[巡逻Agent_Spec]] §7.1
> 归属：`91_实验项目/agent_patrol`
> 目的：办完这份清单，Python Agent 服务才能与飞书建立长连接、收发消息
> 预计耗时：**配置 15-25 分钟** + 版本审核等待（取决于你是否是企业管理员）

---

## 0. 先看结论（三条决定性的前提）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **长连接只支持「企业自建应用」**，商店应用不支持 | 官方文档明确限制 |
| 2 | **不需要公网 IP、域名、HTTPS 证书、内网穿透**，只要 PC 能上外网 | 长连接的核心优势 |
| 3 | ⚠️ **不要把本地服务和 DSH 指向同一个应用** | 长连接是**集群模式、不广播**：同一应用多个客户端时，消息只随机推给**其中一个**。DSH 已占用 `cli_aa4d0673ee389bd8`，复用会导致两边都随机收不到消息 |

所以：**新建一个独立的自建应用**，专供本 Demo。

## 1. 逐步操作清单

> 操作入口：飞书开放平台开发者后台 <https://open.feishu.cn/app>

### 步骤 1 · 创建应用

- [ ] 打开 <https://open.feishu.cn/app> → 点「创建企业自建应用」
- [ ] 应用名称：建议 `巡逻Agent Demo`（或你能一眼认出的名字）
- [ ] 应用描述：可留空
- [ ] 图标：可跳过
- [ ] 创建完成后进入应用详情页

> 若提示需要选择「测试企业」，按引导创建即可（免费，用于开发调试）。

### 步骤 2 · 拿凭证

- [ ] 左侧菜单「**凭证与基础信息**」
- [ ] 记录下这两个值：
  - **App ID**（形如 `cli_axxxxxxxxxxxxxx`）
  - **App Secret**（点「查看」或「复制」）

- [ ] 📌 **把这两个值发给我**（我会放进 `config.yaml`，该文件已在 `.gitignore` 中，不会进版本库）

> ⚠️ App Secret 等同密码，不要贴在任何公开渠道。发给我即可。

### 步骤 3 · 开启机器人能力（**不能跳过**）

- [ ] 左侧菜单「**添加应用能力**」
- [ ] 找到「**机器人**」→ 点「添加」

> 官方「接收消息」事件的前提条件明确要求：**应用需要开启机器人能力**。不开就收不到任何消息事件，这是最常见的第一个坑。

### 步骤 4 · 申请权限

- [ ] 左侧菜单「**权限管理**」→ 搜索并添加下表中的权限

**必需权限（4 个）**

| 权限名称（在后台搜索这个中文名） | 权限标识 | 用途 | 必需 |
|---|---|---|---|
| 读取用户发给机器人的单聊消息 | `im:message.p2p_msg:readonly` | 接收私聊消息 | ✅ |
| 接收群聊中@机器人消息事件 | `im:message.group_at_msg:readonly` | 接收群里 @ 机器人的消息 | ✅ |
| 以应用的身份发消息 | `im:message:send_as_bot` | 发回复、发告警、发卡片 | ✅ |
| 获取与上传图片或文件资源 | `im:resource` | 发抓拍图片（告警卡的核心） | ✅ |

**可选权限（按需）**

| 权限名称 | 权限标识 | 何时需要 |
|---|---|---|
| 获取群组中其他机器人和用户@当前机器人的消息 | `im:message.group_at_msg.include_bot:readonly` | 需要接收其他机器人 @ 本机器人时 |
| 获取用户 user ID | `contact:user.employee_id:readonly` | 需要把 open_id 映射成工号时 |

> 💡 **按中文名搜索，不要按权限标识搜索**。飞书会定期下线重复的历史权限点（官方已下线过一批），中文名比标识稳定。
>
> 💡 `im:message.p2p_msg:readonly` 与 `im:message.p2p_msg` 二者**任一即可**；`readonly` 权限更小，优先选它。

### 步骤 5 · 把订阅方式设为「长连接」（**最关键的一步**）

- [ ] 左侧菜单「**事件与回调**」
- [ ] 找到「订阅方式」设置（可能在「事件配置」或「回调配置」分页下）
- [ ] 选择「**使用长连接接收事件**」→ 点「保存」

> ⚠️ 两处都要确认：**事件配置**和**回调配置**是分开的（一个管事件、一个管卡片按钮回调），如果各自有订阅方式设置，**两处都设成长连接**。
>
> ✅ 选长连接后，页面上不会再要求你填「请求地址 / 请求 URL」，这是正常的——这正是不需要公网 IP 的原因。

### 步骤 6 · 添加事件与回调

**事件订阅**（「事件与回调」→「事件配置」→ 添加事件）

- [ ] 搜索并添加 `接收消息 v2.0`（事件类型 `im.message.receive_v1`）
  - 分类路径：**消息与群组** → 接收消息 v2.0
  - 注意版本选 **v2.0**，不是 v1.0

**回调订阅**（「事件与回调」→「回调配置」→ 添加回调）

- [ ] 搜索并添加 `卡片回传交互`（`card.action.trigger`）

> `card.action.trigger` 是**告警卡片按钮**（确认告警 / 标记误报 / 确认下发任务）能生效的前提。没有它，卡片上的按钮点了没反应。
>
> 注意：它属于**回调订阅**，不是事件订阅。这是第二个常见的坑。

### 步骤 7 · 发布版本

- [ ] 左侧菜单「**版本管理与发布**」→「创建版本」
- [ ] 填写版本号（如 `1.0.0`）与更新说明
- [ ] **可用范围**：至少包含你自己（建议选「全员」或用你的账号）
- [ ] 提交发布
- [ ] 若你是企业管理员：「管理后台」→ 应用管理 → 待审核 → 通过
  - 若不是管理员：需请管理员审核通过

> ⚠️ 这一步可能产生等待时间。**建议今天就提交**，配置和审核可以并行。
>
> 未发布的版本，机器人可能无法正常收发消息。

### 步骤 8 · 验证连通（配完跑一下）

- [ ] 安装 SDK：
  ```powershell
  python -m pip install lark-oapi -U
  ```
- [ ] 保存下面脚本为 `check_feishu.py`，填入 App ID / Secret，运行
- [ ] 用你的飞书账号给机器人发一条私聊消息
- [ ] 控制台出现 `connected to wss://...` 且打印出消息 JSON = **成功**

```python
import lark_oapi as lark

APP_ID = "cli_xxxxxxxx"          # 换成你的
APP_SECRET = "xxxxxxxxxxxxxxxx"  # 换成你的

def on_message(data: lark.im.v1.P2ImMessageReceiveV1) -> None:
    print("[收到消息]", lark.JSON.marshal(data, indent=2))

handler = (
    lark.EventDispatcherHandler.builder("", "")   # 两个参数必须是空字符串
    .register_p2_im_message_receive_v1(on_message)
    .build()
)

cli = lark.ws.Client(
    APP_ID, APP_SECRET,
    event_handler=handler,
    log_level=lark.LogLevel.DEBUG,
)
print("正在建立长连接…")
cli.start()   # 阻塞运行
```

**验证通过后请告诉我**，我就可以开始 M5 的接入开发。

## 2. 踩坑清单（全部来自官方注意事项）

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| 1 | 没开「机器人能力」 | 收不到任何消息事件 | 步骤 3 必做 |
| 2 | 事件选了 v1.0 版本 | SDK 里 `register_p2_...` 收不到 | 添加事件时确认是 **v2.0** |
| 3 | 订阅方式仍是 Webhook | 需要公网地址，本地连不上 | 步骤 5 改成**长连接** |
| 4 | `card.action.trigger` 漏配 | 卡片按钮点了没反应 | 步骤 6 回调订阅里单独添加 |
| 5 | **事件处理超过 3 秒或抛异常** | 触发超时重试，消息重复 | 收到消息立刻返回，耗时逻辑丢后台线程/队列 |
| 6 | **依赖 `event_id` 去重** | 去重失效，重复处理 | ❌ 官方明确：**用 `message_id` 去重，不要依赖 `event_id`** |
| 7 | 本地同时开多个客户端实例 | 消息随机分流，时收时不收 | 长连接是**集群模式、不广播**，本地只跑一个进程 |
| 8 | 与 DSH 共用同一应用 | 两边都随机收到消息 | 新建独立应用（见 §0 第 3 条） |
| 9 | 连接数超限 | 建连失败 | 单应用上限 **50** 个连接，本地开发远用不到，但别写循环重连 |
| 10 | 应用未发布/可用范围不含自己 | 机器人不可用 | 步骤 7 发布并把可用范围包含自己 |
| 11 | 群聊里不 @ 机器人 | 收不到消息 | 群聊策略是**仅 @ 时响应**（与 Spec §7.1 一致） |

## 4. 与现有 DSH 飞书应用的关系

| | DSH 的应用 | 本 Demo 的应用 |
|---|---|---|
| App ID | `cli_aa4d0673ee389bd8` | **新建** |
| 机器人名 | 个人台式机 dsh | 建议「巡逻Agent Demo」 |
| 连接状态 | 已连通（占用中） | 待建 |
| 能否复用 | ❌ **不能** | — |

**不能复用的原因**：飞书长连接是集群模式且**不广播**——同一个应用挂两个客户端，消息只会随机推给其中一个。DSH 已占着那条通道，复用会导致 DSH 和 Demo 都随机漏消息。
