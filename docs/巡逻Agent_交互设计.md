> 文档策略：评审期使用这份不带版本号的活动稿，定稿后再按 vault 规范落 `巡逻Agent_交互设计_V1.0`

## 0. 一句话定义

一个驻留在飞书里的**巡逻业务 Agent**：用户用自然语言下达指令，Agent 完成「取报表 / 下发任务 / 查历史」三类操作，并在异常发生时主动推送。微信通道尚未实现。

**它不是**：机器人的遥控器（不做实时操控）、不是安防平台的替代（不做视频墙）。

---

## 1. 设计约束（决定一切的前提）

这一版的核心约束是 **IM 对话框是"弱 UI"环境**，所以传统界面设计稿不适用，只有四个可控面：

| 可控面 | 飞书 | 微信 | 说明 |
|---|---|---|---|
| 文本 | ✅ | ✅ | 表达能力最弱，只能承载结论 |
| 图片 | ✅ | ✅ | 告警截图的主力载体 |
| 卡片/结构化 | ✅ 交互卡片（按钮、表格、分栏、图片） | ❌ 基本只有文本 | 微信必须降级 |
| 主动推送 | ✅ | ✅ 受限 | 告警实时推送的关键 |

> 上表描述目标通道能力；当前代码只实现飞书，微信一列是后续设计预留。

**由此推出五条硬性交互原则：**

1. **一次回答 ≤ 1 屏**。列表类答案必须限条（默认 5 条）+ 提供"看更多"。IM 里刷屏是不可接受的体验事故。
2. **写操作必须二次确认**。LLM 存在幻觉，绝不允许一句"让机器人去巡逻"就直接对物理世界生效。必须弹确认卡，用户点按钮才执行。
3. **结论在前，明细在后**。先给一句话结论（"昨日 3 条告警，2 条已处置，1 条待处置"），再给明细卡。
4. **图片优先**。告警一律带缩略图，纯文字告警在 IM 里没人会看。
5. **文案不得超出真实能力**。当前检测目标只有两个：`person`（规则近似的人员闯入）与 `chair`（通道占用代理目标），详见 [[巡逻Agent_Spec]] §5.4。**文案不得承诺烟火、翻墙、漏水、徘徊、聚集等当前不具备的能力**。行为判定是规则近似，不得对外宣称「行为识别」。

## 2. 用户角色

| 角色 | 使用频次 | 主要诉求 | 主要入口 |
|---|---|---|---|
| 安保值班员 | 高频 | 看当前状态、处置告警 | 告警推送 → 点按钮处置 |
| 安保主管 | 中频 | 要日报/周报、下发巡逻任务 | 主动发问 + 定时推送 |
| 项目经理/客户 | 低频 | 要周期性汇总、要证据 | 定时报表 |

> **设计取向**：值班员要"快"，主管要"全"。同一份数据要能出两种颗粒度的视图。

## 3. 意图地图

三类核心操作展开为 14 个设计意图：

> 本表包含已实现与规划能力；当前实际接入为飞书，function-calling 工具清单共 13 项。周报与通用 fallback 不属于已实现工具，能力状态以 Spec 附录 A.7 为准。
>
> 写操作的目标交互均要求确认；当前任务取消工具尚未接入确认卡，调用时会直接执行，不能把表中的确认标记当作已实现行为。
>
> **任务创建只响应明确的启动指令**（例如「让机器人去巡逻一圈」）。报表/报告/下载、历史查询、状态和能力咨询都不能生成任务确认卡；即使模型选错工具，系统也会拦截并说明没有创建任务。

| 意图 ID | 触发例句 | 关键槽位 | 输出形态 | 需确认 | 通道 |
|---|---|---|---|---|---|
| `report.daily` | "昨天的巡逻报表" | date | 飞书卡片（指标 + 异常 Top5） | ❌ | 双端 |
| `report.weekly` | "这周整体情况" | week | 卡片（趋势 + 对比） | ❌ | 双端 |
| `report.alerts` | "现在有哪些没处理的告警" | status, level | 卡片列表（带图） | ❌ | 双端 |
| `task.create` | "让机器人去巡逻一圈" | route/points, time, repeat | **确认卡 → 回执卡** | ✅ | 双端 |
| `task.list` | "有哪些任务在跑" | status | 卡片列表 | ❌ | 双端 |
| `task.cancel` | "把今晚 10 点那个任务停了" | task | 确认卡 → 回执 | ✅ | 双端 |
| `history.query` | "上周有没有人员闯入的告警" | time range, scene, algo, point | 卡片表格（≤5 条） | ❌ | 飞书优先 |
| `history.export` | "把最近 7 天的告警导出 CSV" | range, filters | 告警明细 CSV 文件 | ❌ | 飞书已实现 |
| `report.patrol.export` | "导出今天的巡逻报告 PDF" | date | 逐轮、逐点位结果与图片 PDF | ❌ | 飞书已实现 |
| `robot.status` | "机器人现在在哪" | robot | 文本 + 状态卡 | ❌ | 双端 |
| `snapshot.now` | "拍一张现在的照片" | point | 图片 | ❌ | 双端 |
| `alert.handle` | "第 2 条是误报" | alert id, action | 确认 → 回执 | ✅ | 双端 |
| `help` | "你能做什么" | — | 能力清单卡 | ❌ | 双端 |
| `fallback` | 无法识别 | — | 澄清追问（给 2-3 个候选） | — | 双端 |

**槽位缺失处理**：不追问超过 1 轮。缺 `route` 就列出可选路线让用户选；缺 `date` 默认今天。**绝不做多轮问卷式交互**——IM 里的多轮追问流失率极高。

## 4. 核心对话流

### 4.1 取报表（最高频）

```
用户：昨天的巡逻报表
Agent：📊 巡逻日报 · 2026-10-12
       ━━━━━━━━━━━━━━━━
       ✅ 任务完成 6/6    覆盖率 98.2%
       ⚠️ 告警 3 条       待处置 1 条
       🔋 无异常         离线 0 次
       ━━━━━━━━━━━━━━━━
       重点异常：
       1. 👤 人员闯入 · 东侧通道 · 14:22  [已处置]
       2. 🚧 通道占用 · 西侧通道 · 09:15  [已处置]
       3. 👤 人员闯入 · 东侧通道 · 23:41  [待处置] ⚠️
       [查看全部 12 张抓拍] [看本周趋势]
```

**设计要点**：数字用 emoji 做视觉锚点，让主管 3 秒内抓住关键。异常项必须带处置状态——这是主管最关心的字段。

### 4.2 下发任务（含二次确认，最关键流程）

```
用户：让机器人去巡逻一圈

Agent：📋 任务确认
       路线：标准巡检路线（2 个点位）
       时间：立即执行一次
       预计：约 1 分钟
       点位：东侧通道 → 西侧通道
       [✅ 确认下发] [✏️ 修改时间] [❌ 取消]

用户：（点击「确认下发」）

Agent：✅ 任务已下发（T-20261013-004）
       机器人 R-01 已出发 · 当前位置：东侧通道
       完成后自动推送结果。
```

**设计要点**：

- 确认卡必须**把 Agent 的解析结果摊开**（路线、点位、时间），让用户能验证 LLM 理解对不对。这是防幻觉的核心机制。
- 提供"修改时间"而非"重新输入"，把纠错成本降到一次点击。
- 回执带任务号，后续可以用任务号追问。

### 4.3 查历史

```
用户：上周有没有人员闯入的告警

Agent：🔍 历史查询  2026-10-06 ~ 2026-10-12
       条件：告警类型=人员闯入
       ━━━━━━━━━━━━━━━━
       共 2 条：
       1. 10-12 14:22 · 东侧通道 · 置信度 0.87 · 已处置
          [查看抓拍]
       2. 10-08 21:05 · 东侧通道 · 置信度 0.54 · 误报
          [查看抓拍]
       ━━━━━━━━━━━━━━━━
       [导出 CSV] [换个条件]
```

**设计要点**：命中 0 条时必须明确说"没有"，并提示放宽条件（"要不要看全部异常类型"），不能给一个空卡片让人困惑。

> **注意**：这里展示的是**映射后的原始 COCO 置信度**，不是"安防语义的可信度"。若客户追问，要能一路回溯到 `person` 的原始输出（见 [[巡逻Agent_Spec]] §8 可追溯性要求）。

### 4.4 导出逐点巡逻 PDF

```text
用户：导出今天的巡逻报告 PDF

Agent：📄 生成并发送「巡逻报告 PDF」
       报告按巡逻轮次展开路线中的每个点位，列出绑定算法、阈值、检测摘要、任务状态和图片证据。
       异常点位使用带检测框的算法结果图；正常点位使用原始拍照图。
       未执行点位标为「未完成」；历史照片文件缺失会单独提示。
```

明确给出日期或任务号时直接生成 PDF。未指定范围时展示「最近一次 / 按天 / 按周 / 按月 / 指定任务」范围卡；按天/周/月继续展示有巡逻记录的日期或周期，指定任务展示最近 10 次巡逻。更早任务可直接输入任务号；也可选择最近一次单轮直接导出。

单次任务/轮次报告仅任务发起人可导出；日/周/月报告是当前系统中的共享汇总，不按角色隔离。

周按自然周（周一至周日），月按自然月。该 PDF 是巡逻结果报告，不等同于告警 CSV：即使某点位没有异常，也会显示其正常结论和原始照片。旧轮次只有在能从检测记录和磁盘图片回补到证据时才会显示结果，不会把无记录误判为正常。

### 4.5 告警主动推送 + 就地处置（闭环价值最高的场景）

```
Agent：（主动推送）
🚨 新告警 · 人员闯入
点位：东侧通道    时间：14:22:07
置信度：0.87      机器人：R-01
[图片缩略图]
[✅ 确认告警] [❌ 标记误报] [👀 查看详情]

用户：（点击「标记误报」）

Agent：（卡片就地更新为）
✅ 已标记为误报 · 处理人：张工 · 14:25
（该记录已从待处置列表移除）
```

**设计要点**：**就地更新原卡片**（飞书支持 `patch` 卡片），而不是回一条新消息。这让告警卡片本身成为可操作的状态机，避免消息流里散落重复告警。

## 5. 消息卡片结构规范

### 5.1 飞书（四个标准模板）

| 模板 | 用途 | 结构 |
|---|---|---|
| `report_card` | 日报/周报 | 标题 → 指标栅格(3列) → 分隔线 → 异常 Top N → 按钮组 |
| `confirm_card` | 所有写操作 | 标题 → 键值对明细 → 按钮组（确认/修改/取消） |
| `list_card` | 历史查询/列表 | 标题+条件摘要 → 分隔线 → 条目（标题+元信息+缩略图） → 分页按钮 |
| `alert_card` | 告警推送 | 红色标题 → 点位/时间/置信度 → 图片 → 处置按钮组 |

`alert_card` 与 `confirm_card` 都必须是**可更新的**（记住 `message_id`，处置后 patch 原卡片）。

### 5.2 微信降级规则

| 飞书能力 | 微信降级方案 |
|---|---|
| 交互卡片 | 纯文本 + 编号条目 |
| 按钮 | 文本指令：回复 `1` 确认 / `2` 取消 |
| 指标栅格 | 单行文本 `完成 6/6 | 告警 3 | 待处置 1` |
| 表格 | 缩进文本列表，超 5 条截断并提示"回复 6 看更多" |
| 图片 | ✅ 直接发图 |

> **微信侧方案尚未实现**：交互退化为"编号回复"协议仅是设计预案，当前不要对用户承诺可通过微信使用。

## 6. 兜底与异常处理

| 场景 | 处理 |
|---|---|
| 意图无法识别 | 给 3 个最可能的候选 + "看看我能做什么" |
| 槽位指向的对象不存在 | 列出可选项，不猜测 |
| 机器人离线/忙碌 | 明确告知状态 + 建议（"R-01 正在执行 T-003，预计 8 分钟后空闲"） |
| 任务下发失败 | 回执卡标红 + 失败原因 + 重试按钮 |
| 报表数据缺失 | 说明缺失原因（"该日期无巡逻记录，机器人 10-11 全天离线"） |
| LLM 超时 | "正在查询，稍等…" 占位 → 结果到了 patch 更新 |
| **用户问超出能力范围的事**（如"昨晚有没有烟火"） | **如实说明当前不具备该检测能力**，不编造，并提示可查的告警类型。这是信任底线 |

## 7. 待评审决策点

- [ ] **D1** 微信通道形态：企业微信自建应用 / 微信客服 / 个人微信（**个人微信无官方 API 且有封号风险，不建议**）
- [ ] **D2** 告警是否需要"分级"（紧急/一般/提示）以及各级的推送策略（是否 @ 全员、是否只私聊值班员）
- [ ] **D3** 报表默认推送时间与对象（现在设想：每日 08:30 推送给主管私聊）
- [ ] **D4** 是否需要"人机协巡/远程遥控"（现在明确排除在 V1 之外）
- [ ] **D5** 多机器人：V1 单机演示还是直接做多机？（影响数据模型，但模型已预留 `robot_id`）
- [x] **D6** 导出格式：巡逻结果使用逐点 PDF；告警明细可单独导出 CSV（飞书文件发送已接入）
- [ ] **D7** **报表里是否显示"检测能力边界"说明**（让客户清楚哪些场景已覆盖、哪些未覆盖）——建议显示，可显著降低期望错位
