# 巡逻 Agent Demo

在**没有实体机器人**的前提下，用一台带摄像头的 PC 搭出可端到端演示的安防巡逻 Agent：
用户在飞书聊天框里用自然语言完成「取报表 / 下发任务 / 查历史」，巡逻产生的告警实时推回飞书并可就地处置。

> 一条命令跑起来，5 分钟演示完整闭环。详细设计见配套文档（见文末）。

---

## 它能做什么

| 能力 | 说法示例 | 输出 |
|---|---|---|
| 取报表 | 「昨天的巡逻报表」 | 日报卡片（完成率、覆盖率、告警数、重点异常） |
| 导出报告 | 「导出今天的巡逻报告 PDF」 | 按轮次和点位汇总结果、算法判断与现场图片 |
| 下发任务 | 「让机器人去巡逻一圈」 | **确认卡 → 点确认 → 真下发** |
| 查历史 | 「上周有没有人员闯入的告警」 | 历史查询卡片 |
| 看机器人 | 「机器人现在在哪」 | 状态卡片 |
| 抓拍 | 「拍一张现在的照片」 | **带检测框的算法结果图** |
| 处置告警 | 点卡片上的「标记误报」 | 卡片**就地变绿** |
| 能力边界 | 「昨晚有没有烟火告警」 | 如实回答「本版本不具备」 |

---

## 架构

两个独立进程，通过 HTTP 通信：

```
      飞书用户
         │  长连接 (WebSocket)
         ▼
┌─────────────────────┐        ┌──────────────────────┐
│  Agent 服务  :8200   │  HTTP  │ 机器人模拟器  :8100   │
│                     │ ─────► │                      │
│  · 飞书接入(长连接)   │        │  · 虚拟机器人 R-01     │
│  · LLM 编排 + 工具    │ ◄───── │  · 摄像头采集          │
│  · 报表引擎 + 卡片    │  回调  │  · YOLO 真实推理       │
│  · 会话记忆           │        │  · 场景映射 + 落库     │
│  · 定时日报推送       │        │                      │
└─────────┬───────────┘        └──────────┬───────────┘
          │                               │
          └──────────► SQLite ◄───────────┘
```

**为什么拆成两个进程**：将来把模拟器换成真机或真平台时，**Agent 服务一行都不用改**。
这是整个项目最重要的架构决策。

## 快速开始

### 1. 环境

```powershell
# 必须用项目自己的 venv（不要用系统 python，可能污染其它工具的环境）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 2. 配置

```powershell
copy config\config.example.yaml config\config.yaml
# 然后填入飞书应用凭证与 LLM API Key
```

飞书侧需要：**新建自建应用** → 开启机器人能力 → 订阅方式选「使用长连接接收事件」
→ 授予 4 项权限 → 订阅 2 个事件（`im.message.receive_v1`、`card.action.trigger`）→ 发布。

### 3. 起服务

```powershell
# 终端 1 — 机器人模拟器
.venv\Scripts\python.exe -m uvicorn robot_sim.main:app --port 8100

# 终端 2 — Agent 服务
.venv\Scripts\python.exe -m uvicorn agent_service.main:app --port 8200
```

### 4. 造点历史数据（可选，但强烈建议）

```powershell
.venv\Scripts\python.exe scripts\seed_demo.py --days 7 --reset
```

不造的话，「上周有没有…告警」这类问题会一律返回 0 条，演示效果差。

### 5. 开始用

给飞书机器人发一条私聊消息：**「你能做什么」**。

## 脚本一览

| 脚本 | 用途 |
|---|---|
| `check_feishu.py` | 飞书凭证与机器人能力自检（不依赖长连接） |
| `listen_feishu.py` | 飞书通道全链路验证（收/发/图/卡片/按钮/PATCH） |
| `check_llm.py` | LLM 连通性 + **function calling** 能力验证 |
| `probe_camera.py` | 摄像头 + YOLO 实测（无人值守采样，评估检出率） |
| `smoke_robot_sim.py` | 机器人模拟器冒烟测试（自动时间快进跑完一轮） |
| `test_agent_local.py` | **脱离飞书**测编排层（LLM + 工具 + 卡片） |
| `seed_demo.py` | 造演示历史数据 |
| `capture_once.py` | 触发一次抓拍，打印结果图路径 |

排查问题时**从内往外**测：`test_agent_local.py` → `smoke_robot_sim.py` → `listen_feishu.py`。
这样能把「LLM/工具/卡片」的问题和「通道」的问题分开定位。

## 点位绑定算法（核心概念）

**一个算法 = 一类检测能力。点位绑定一个算法，然后只上报这个算法的检测结果。**

```
                        ┌──────────────────────────┐
   P1 东侧通道  ──绑定──►│ person_intrusion         │
                        │ 人员闯入检测 · person     │──► 只上报「人员闯入」
                        └──────────────────────────┘
                        ┌──────────────────────────┐
   P2 西侧通道  ──绑定──►│ corridor_occupancy       │
                        │ 通道占用检测 · chair      │──► 只上报「通道占用」
                        └──────────────────────────┘
```

配置在 `config/mapping.yaml` 的 `algorithms`（算法定义）
和 `config/routes.yaml` 的 `points[].algorithm`（绑定关系）。

**绑定生效的范围**（实测：P2 同一帧里同时检出 `person 0.92` 与 `chair 0.53`）：

| 输出 | 是否受绑定约束 |
|---|---|
| 告警 | ✅ 只有绑定算法产生告警 |
| 算法结果图上的框 | ✅ 默认只画绑定算法的框，画面里的人不会被标注 |
| 「拍一张照片」的文字回显 | ✅ 只报绑定算法的检出 |
| 内部检测表留档 | ⚙️ 由 `detector.store_all_classes` 控制（默认保留全类别，**这不是「上报」**） |

> 点位没绑算法会**直接报错**，不静默降级 —— 一个不知道要检测什么的点位，早点失败比默默跑强。
> 同时 `target_label` 不再单独配置，而是从绑定算法派生，避免「点位写 person、算法却是通道占用」这种自相矛盾的配置。

## 检测能力边界（重要，请如实对外）

YOLO COCO 80 类**覆盖不了多数安防场景**，本 Demo 只用两个算法：

| 算法 ID | 名称 | 模型类别 | 映射告警 | 等级 |
|---|---|---|---|---|
| `person_intrusion` | 人员闯入检测 | `person` | 人员闯入 | 紧急 |
| `corridor_occupancy` | 通道占用检测 | `chair` | 通道占用 | 一般 |

**做不到的**：烟火烟雾、翻墙攀爬、聚众冲突、抽烟、漏水、围栏/门窗破损、消防设施损坏、照明失效 ——
这些在 COCO 里没有对应类别，本版本**明确不做，也不用模拟数据凑数**。

升级路径：换开放词汇检测模型（YOLO-World / GroundingDINO），用文本 prompt 直接检
`fire` / `smoke` / `wall damage` 等自定义词。

另外「闯入」本质是**行为**，而 COCO 只提供 `person` 框。本版本的判定是
「点位检出 person 且置信度达标」，属于**规则近似**，不宣称具备行为识别能力。

## 数据与证据链

每次拍照落**两张图**，巡逻轮次还会为每个点位持久化检测结论和两张图的路径：

| 文件 | 内容 | 用途 |
|---|---|---|
| `<base>.jpg` | 标注帧，带检测框与标签 | 推送给用户、报表展示 |
| `<base>_raw.jpg` | 原始帧，零绘制 | **证据本体** |

数据库中 `detection` 与 `alert` **故意分离**：

- `detection` 存**原始 COCO 输出**（全类别，不按点位过滤）
- `alert` 存**映射后的业务语义**（人员闯入 / 通道占用）

这样客户追问「你凭什么说这是人员闯入」时，能一路回溯到原始模型输出、
置信度、抓拍图像与发起人。**每条告警都能溯源到 `detection → patrol_run → task → 发起人`。**

`detection.is_mock` 区分数据来源：`0` = YOLO 真实推理，`1` = 模拟数据。
**模拟数据绝不允许与真实推理混淆**，报表会显式标注。

## 设计上踩过的坑（留作记录）

| 坑 | 现象 | 教训 |
|---|---|---|
| 把卡片写成 `[卡片] 标题` 存进对话历史 | LLM 学会这个"格式"，不再调工具，直接吐一句没有数据的假卡片文案 | **任何可模仿的输出模板都不能进 assistant 轮次**。卡片/图片一律不写历史 |
| 卡片回调同步处理 | 超过 3 秒触发飞书超时重试，且长连接单线程被堵住，后续消息一起变慢 | 回调**必须 3 秒内返回**：立刻回 toast，干活丢后台，干完 PATCH 就地更新 |
| LLM 不知道当前日期 | 「昨天」被解析成训练数据里的日期 | **system prompt 必须注入当前日期**，否则所有相对时间全错 |
| 用 `event_id` 去重 | 去重失效 | 飞书官方明确：**用 `message_id` 去重，不要依赖 `event_id`** |
| 摄像头每次抓拍重开 | 首次打开实测要 6 秒，演示明显卡顿 | 模拟器**常驻持有**摄像头 |
| 依赖 PATH 里的 python | 本机 PATH 指向另一个工具的 venv，装 torch 会污染它 | **项目独立 venv**，所有命令走 `.venv\Scripts\python.exe` |

## 已知限制

- 单机单点位共享一台摄像头，两个点位的画面完全相同，靠业务标签区分
- 历史 seed 数据无抓拍图（是脚本编的，不是真实抓拍）
- 微信通道未接入（飞书已验证完整，微信计划下一版）
- 支持按日导出逐点位 PDF 巡逻报告；告警明细仍可按需导出 CSV
- 周报未实现
- 行为判定为规则近似，非行为识别模型
